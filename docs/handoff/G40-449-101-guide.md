# G40-449 — the 101-guide half, and why it is a patch instead of an edit

**Status: PREPARED, DELIBERATELY NOT APPLIED. Apply when the store build ships, not before.**

Owner rule (standing rules §5): *a user-facing change is not done until its 101 guide is updated.*
G40-449 changes what the **Prioritize MY Gophers** section *does* on the requester's Request
Details screen, so the guide owes an update.

Follows the same shape as `G40-450-101-guides.md` — same reasons, same two failure modes it avoids.

## What changed in the product

The checkboxes under **Notify One Of MY Gophers** rendered **ticked** while the value the app
actually submitted was **empty**. So tapping a name *deselected* it, and touching nothing at all
still submitted **zero** hand-picks — while the list looked fully selected. Order **65228**
(2026-09-06) lost both picks that way; 10 of 42 orders in the preceding week recorded none.

After the fix the tick is derived from the submitted value, so the two cannot disagree:
**switching the toggle on selects every saved MY Gopher, and the requester unticks anyone they
want to skip.**

## Why the guide has to change, and not only the code

The current sentence reads:

> Once you've saved at least one, the **Prioritize MY Gophers** option appears here: pick which
> saved Gophers to notify and they get **first dibs**.

*"Pick which saved Gophers to notify"* describes a **start-from-nobody** interaction. The fix
deliberately starts from **everybody** — because that is what the section already rendered, and
per the owner's 2026-09-06 note it is what affected requesters believed had happened. A guide
that says "pick" when the screen arrives pre-ticked is the same class of mismatch that caused
the defect, just moved into the documentation.

The replacement clause says the default out loud and names the way out:

> …switch it on and **every** saved Gopher is ticked to be notified — untick anyone you'd rather
> skip this time — and whoever stays ticked gets **first dibs**.

Nothing else in the paragraph changes. The surrounding sentences — the dashboard collection,
**Hire Again**, the broadcast-window fallback, approval for workers outside MY Gophers — were
already accurate and are left alone.

## ⛔ Why it is not applied yet

The other half of the same rule is the honesty standard from the June `gopher-request.html` copy
work: **the guide describes what the product does, not what it will do.**

The new behaviour does not exist on anybody's phone. There is no OTA path in either mobile repo —
Appflow Live Updates is not enabled — so it reaches users **only through a store release**.
Applying this now would tell a real requester that switching the toggle on selects everyone, on a
build where it selects nobody. That is not a small inaccuracy: it is the *precise* false belief
that made the bug cost something.

## ⛔ Why it is a patch file and not an uncommitted edit

`scripts/deploy.sh` reads the **working tree** (`SRC="$REPO/Final"`) and ships the whole of
`Final/`. An uncommitted edit sitting in `Final/gopher-request-101.html` is published by the next
`--allow-dirty` run by *any* session — standing rules §3: "committed but not deployed" is not a
durable state, and neither is "uncommitted but nobody will deploy today". A patch under
`docs/handoff/` is outside `Final/` and cannot ride along.

This branch therefore contains **no change to `Final/`**. Verified: `git status` shows the guide
clean, and the patch was round-tripped — applied, the new copy confirmed present, then reverted.

## How to apply

```bash
git apply docs/handoff/G40-449-101-guide.patch
```

Then deploy `Final/` as normal, and delete this file and the patch — a prepared change that has
been applied is just clutter that reads as pending.

**Baseline this patch was cut against** — blob `5f8ce678303b208bd3567ec977180a87c253c2f2`, which when the patch was
made (2026-09-10) was the content of *all three* of: the working tree, `HEAD:Final/gopher-request-101.html`,
and the deployed `origin/main:gopher-request-101.html`. The live URL was also content-verified to
carry the old clause. So the patch targets exactly what is published.

Check before applying:

```bash
git rev-parse HEAD:Final/gopher-request-101.html   # expect 5f8ce678303b208bd3567ec977180a87c253c2f2
```

If that differs, the guide has moved on — read the note below rather than forcing the patch.

⚠️ **This branch is rooted on `origin/feature/deals-google-maps-audience`, whose copy of the guide
is OLDER than the baseline above.** That is deliberate and harmless: the commit adds only these two
files under `docs/handoff/`, and `git apply` runs against the working tree at apply time, not
against this branch's base. Rooting it here was the only way to push without also publishing 22
unrelated commits from other sessions into this **public** repo.

⚠️ If the guide has moved on before then, `git apply` will reject. **Re-read the surrounding copy
rather than forcing it** — standing rules §5 exists because a minimal find-and-replace on the
Deals 101 is what created that rule in the first place.

✅ **The Go guide needs nothing — checked, not assumed.** `gopher-go-101.html` mentions MY Gophers
exactly once, on the worker side, in the request-type list:

> **MY Gopher (Favorite)** — You were requested **by name**. It's yours alone (and other Favorites)
> for the first full minute — one minute before it opens to any other tier.

*"Requested by name"* **is** the hand-pick, so that copy is already correct, and the fix makes it
more often true rather than less: a worker who should have had that window frequently was not given
it, because the hand-pick never reached the server. No edit, and none is being withheld.

(Separately, and **not** this ticket: "the first full minute" against the live cadence of favourites
at 1 s and the next tier at 60 s is a ~59-second head start, which the truth doc already records.)
