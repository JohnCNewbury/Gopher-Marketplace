Ink on green: now vs proposed

The Request referral tab row, rendered twice. Every value is lifted verbatim from gopher-request.html — same font, weight, size, padding, radius and green. The only difference between the two panels is the ink colour, and that colour comes from one token, --ink-on-green, on one line.

Now --ink-on-green: #ffffff
1.85:1 Fails AA

White on Shamrock. The style guide rates this pair 2.0:1 — FAIL, and names it outright: “bright greens don’t carry white type.” There is almost no luminance step between ink and fill, so the glyph edges have nothing to resolve against — which is the softness you spotted.

Proposed --ink-on-green: #002461
7.95:1 Passes AAA

Midnight Blue on Shamrock — the guide’s rated pairing at 7.8:1 AAA. Nothing else changes: same green, same type, same shape. The guide calls this “not a style preference — an accessibility requirement.” 

gopher-request.html:6536
- :root { --ink-on-green:#ffffff; }
+ :root { --ink-on-green:#002461; }

That is the whole edit. One line, one value. It governs 33 green surfaces across Request — tabs, primary CTAs, selected chips, checkmarks, the sent-message bubble — because every one of them already asks for var(--ink-on-green) and is currently handed white. Nothing else in either file needs to move for this to take effect.

Worth knowing before you call it: that line arrived with the login-portal CSS grafted in from Connect, where white was wanted for a navy portal button. Because it was written at :root it went global and hit all 33. Connect already sets this token to #002461 — so this change makes Request agree with Connect, rather than introducing anything new.

You are looking at this on your own Mac, at your own pixel ratio — which is exactly where the judgement should be made. The browser pane I audit in runs at 1x and yours does not.
