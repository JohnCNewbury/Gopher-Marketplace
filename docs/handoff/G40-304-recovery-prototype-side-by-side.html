G40-304 — Recovery modal: the prototype today vs what production shows

Side-by-side FIRST, per the 2026-08-19 rule. Nothing in the prototypes has been changed. Left is what Final/gopher-request.html, Final/gopher-connect.html and _prototypes/Request/gopher-request-home.html render today; right is the sheet that shipped in the Request app 3.9.2 (device-verified by you on 2026-09-02/03, live behind GOPHER_RELEASE_ENABLED=true since 2026-09-07), rendered in the prototype's own modal chrome.

Why this is being proposed. Standing rule 12: where a prototype disagrees with shipped behaviour, the prototype is the bug. The July prototype offers three options, mints a new order #, and has an edit-as-new form. Production keeps the same order #, refuses edits while released (Stripe will not change the amount on a held authorization — your option B, 2026-09-02), shows the Gopher's stated reason, and runs the clock from the server. Anyone building from the prototype today builds the dead model.

What changes if you approve. One commit touching the three recovery modules (web Request, web Connect, Request phone prototype) so they render the right-hand sheet: two options, same order #, reason box, no edit form, the countdown reading from a "server" deadline in the demo. The Go prototype already releases rather than cancels (2026-07-17), so it is unchanged. Rule 12b: web and prototype in the same pass.
One thing only you can rule on. The July prototype let the requester rate the Gopher who cancelled on the Cancel path (G40-9 AC4). The shipped 3.9.2 sheet does not — Cancel refunds and closes. The canonical flow doc has carried this as an open question since Jul 12 ("whether this flow may skip rating needs an owner ruling"). If rating the departed Gopher should exist, it is a client change and its own ticket; the prototype should then keep a rating step. If not, the prototype drops it, matching production.
