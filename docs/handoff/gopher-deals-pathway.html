End-to-end architecture

How a deal travels — from sign-up to the customer's tap.

Two marketplaces share one system: merchants post promos with last-mile delivery, and Local Pros post defined-price services. Every stage below is built in the prototype — click any stage to see the exact code seams.

Grounded in gopher-deals.html, gopher-request.html, gopher-connect.html · companion to gopher-deals-pathway.md

DLM — Merchant / last-mile

A local business (restaurant, retail, convenience, age-restricted)
  • Deal: a promo/offer + optional code
  • Redeem: order on their site, or parlay into a Gopher delivery
  • Reach: customers & workers within 25 mi of the business

DLP — Local Pro / provider

An existing Worker who qualifies for the Service-Provider tier
  • Deal: one honest defined price for a service
  • Register: eligibility funnel on the web → deal posted in the Gopher Go app
  • Redeem: a provider-directed request, auto-accepted
  • Reach: up to 50 mi, set in the Gopher Go app

Provider — a two-entry flow DLP

Entry A · public eligibility funnel (gopher-deals.html) — the "I'm a Service Provider" card collects only First, Last, SMS, Email, Gopher ID (the ⓘ points to Refer & Earn). Submit → "we'll email you eligibility terms + next steps + a Gopher Go inbox message." No deal, price or reach here.

Entry B · in-app deal form (gopher-go.html) — an eligible worker taps "Offer My Service →" above Profile and posts the deal minus personal: earn → customer pays ×1.10 (Deal Boost), normal → struck ×1.10, and a 1–50 mi reach slider (capped 50). Not eligible → the button locks and redirects to gopher-go-101.html#offer-deals.

Where the info goes — today

  • Writes a local backup → localStorage['gopherLeads'] :3702

  • Console escape hatch: downloadGopherLeads() :3719 exports the backup as CSV

This is the current persistence layer. There is no deals database yet — a "lead" is a Sheet row. Production replaces the endpoint behind this same seam; until then, the Sheet is the merchant pipeline.

Data model Built

▾

Defined in the ACCOUNT object at gopher-deals.html:4943:

ACCOUNT one owner login
business { id, name, tagline, color, locations[] }

deal authored per-location

The load-bearing rule — deals are location-bound

  • Each deal ties to exactly one location. That location's ordering site and the parlayed pickup both resolve to that address.
  • To offer elsewhere, the owner adds a location :5189 and submits a new deal there — no "one deal, many locations" fan-out. Keeps pickup unambiguous.
  • Mobile / food-truck sets mobileAddress:true applyMobileAddr() :5037 — this is what makes redemption ask the customer for a pickup address.

Authoring: the New-Deal form has a business/location picker populateLocationSelect() :4970 that pre-fills from the last deal at that location prefillFromLocation() :4980.
